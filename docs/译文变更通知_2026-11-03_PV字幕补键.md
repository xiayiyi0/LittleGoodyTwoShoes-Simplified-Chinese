## 2. 为什么它们以前是英文（机制，别再按「漏翻」处理）

第二首歌的字幕**不是整条记录上屏**，而是逐条替换。游戏侧逻辑（`LGTS.Cinematics.Subtitles.SubtitlesManager.Awake`）：

```csharp
PlayableDirector pd = GetComponent<PlayableDirector>();
int index = 0;
foreach (TimelineClip clip in ((TimelineAsset)pd.playableAsset).GetRootTrack(1).GetClips())
{
    string term = subtitleSO.codes[index];   // ← 逐条取 codes
    LocalizationMediator.GetTranslation(ref term);
    ((SubtitleClip)clip.asset).subtitleText = term;
    index++;
}
```

由此产生两个后果：

1. **`codes` 数组比 clip 数短时，循环抛 `IndexOutOfRangeException` 提前结束**，
   后面几条 cue 保持时间轴作者写死的英文，既不来自 gridly/i2，也不在译本 CSV 里；
2. 即便逐字比对，**它们的英文措辞与 CSV 英文列并不相同**：

| CSV（gridly）英文 | 实机字幕英文 |
|---|---|
| `Will I be able to reach the end of this journey\nwhose final act is heralded by the brilliant light...` | `Will I be able to reach the end of this<br> journey whose final act is heralded` |
| `that engulfs visions I stow so deep in my bosom?` | `By the brilliant light that engulfs visions<br> I stow so deep in my bosom?` |

所以「按英文建键」这条路对它们永远不成立——这也是为什么此前按 59 种形态穷举、
`缺键 0` 的自检仍然漏掉这两句：穷举的样本来自译本英文列，而实机串是另一份文本。

## 3. 键生成口径（新同学必读）

- 归一：去富文本标签 → **`<br>` 直接删除（不补空格）** → `\s+` 折叠为一个空格；
- 因此同一句歌词可能有三种形态，**要各自建键**：
  1. **整条**：一条记录整段上屏；
  2. **粘合**：`A<br>B` → `AB`（与 `A B` 是两个不同的键）；
  3. **逐行**：时间轴把整条拆成单句逐条推。
- 记录行译文进 **CSV**；时间轴逐句 / 改写过的串进 **`tools/runtime_lines.txt`**。
  `runtime_lines.txt` 的优先级高于 CSV 候选，`verify_release.py` 把它算作「译本已覆盖」。
